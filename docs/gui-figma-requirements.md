# ForgeSched GUI — Figma 设计需求 v0.1

日期：2026-10-12。状态：产品/交互方案，供评审和 Figma 画稿；不是已实现功能清单。
依据：当前 P17 API、worker/forge_worker.py、worker/pjtest_adapter.py、server/clock.py。

## 1. 目标与页面组织

面向在内网使用 ForgeSched 的回归测试工程师。首版完成三个操作：看工作服务器与 slot，
用 test2 目录树选择 testcase 并提交任务，查看批次结果和每次执行的完整日志。
中文界面，桌面宽屏优先；建议以 1440×900 为主画板，窄窗口仍可折叠侧栏。
使用清晰紧凑的工程工具风格，状态同时有图标和文字，不只靠颜色。

左侧导航：工作机、任务与回归、添加任务、定时计划。添加任务同时提供醒目的全局按钮。
顶部显示当前调度服务连接名称、连接状态、最后刷新时间。设置中配置连接；连接信息
从统一配置读取。这里的“工作服务器”是 novarch3/novarch4；“调度服务”是 ForgeSched。
二者在文案和布局上区分，避免把 slot 和调度服务器混为一谈。

## 2. 工作机：按工作服务器名分栏，点击展开 slot

主页面以工作服务器名为分组栏/卡片，例如 novarch3、novarch4。机器数量多时使用
可搜索的分组列表，避免几十个并排列。每栏显示在线 slot 数/已注册 slot 数、忙碌数、
空闲数、离线数与最近更新时间。点击机器名打开右侧详情，或进入机器详情页。

详情内按 slot 展示：slot1、slot2、slot3；列包含连接状态、运行/空闲、当前 task_id、
testcase、revision、flow、开始时间。点击任务跳到执行详情，点击 slot 查看 slot 信息。
连接状态 ONLINE/OFFLINE/DRAINING 与忙碌/空闲分开；ONLINE 不等于空闲。
机器分组摘要由 slot 推导，可显示“全部在线/部分离线/全部离线”，不伪装成独立的
manager 心跳。已断开的 slot 留在列表，不因离线立刻消失。

搜索按机器名、slot 名；筛选在线、离线、排空中、忙碌、空闲。自动刷新保留展开项和
选择项。服务连接丢失时保留最后一次数据，并明显标记“数据未更新”；不能改成空列表。
加载中、尚无工作机、筛选无结果分别设计。

扩展操作：机器/slot 的“停止接新任务”和“恢复接任务”预留位置，按能力开关展示。
停止接任务是排空：当前 testcase 继续跑完。不是关机，也不是杀进程。
首版未具备远程控制 API 时，不提供可点击且显示成功的按钮。

后端现状：query_workers 有机器/slot、连接状态、容量、占用、心跳；任务摘要可关联
worker_id，但该关联不是同一事务快照。详细当前任务信息需补查询/聚合。
Worker 库存目前只在当前 Server 进程内保留；跨 Server 重启的机器历史需后续持久化。

## 3. 添加任务：目录树勾选 + 参数 + 提交预览

任务来源改为 Server 的 test2 testcase 目录。GUI 不要求用户编写 runlist 文件。
Server 维护可选择目录；Worker 仍执行下发的相对 case 路径。
目录选择与业务 target 是两个字段，不能把任意目录名直接写成现有 target。
target 的统一含义需在后端对齐，尤其现有手工提交用器件名、clock 提交用模板名的差异。

页面左侧为搜索和目录树，右侧为任务参数、已选项摘要；底部固定显示已选 case 数、
预计任务数、“预览提交”“清空选择”。示意：

```text
test2
  [−] kintexuplus
      [−] xcku3p-ffvd900-1-i
          [✓] convergentRoundingEven
              [✓] run.tcl
          [ ] anotherCase
              [ ] run.tcl
```

叶子执行单位是 run.tcl。case 目录可作为友好的可选节点，但只能对应扫描发现的
case；勾选一般目录代表选择其下全部可执行 case。复选框有未选、全选、半选三态。
打开目录和勾选目录是独立动作。界面保留路径层级，也支持展开/收起全部。
展示叶子总数、选中数；点击已选摘要可定位回树节点。

搜索按目录名或相对路径，显示匹配路径及祖先。搜索过滤不能取消已选项。
“勾选目录全部 case”包含未加载子目录；“选择搜索结果”单独提供明确按钮，不能混用。
大目录懒加载/虚拟滚动；父目录计数和全选范围由 Server 解析，不只选当前可见节点。
Server 只允许扫描配置的 work_root，避免软链接越界、目录循环和浏览任意系统路径。

参数包含：批次名称、版本（来自可用 GalaxCore ZIP 列表，可手输但需校验）、flow 模板、
优先级、单 case 超时。首版一次提交使用一个 flow 模板；多 flow 后续支持。
配置由 Server 模板展开；预览显示实际 flow_config，提交时固定快照。
本次选择也固定成去重后的相对路径清单，目录随后变化不会改变已提交批次。
可保存本地未提交草稿；调度执行所需参数仍以 Server 校验为准。

预览展示批次名称、revision、case 数、flow、实际 flow_config、总任务数、可展开的
case 清单和校验错误。空选择、ZIP 不存在、case 消失、模板失效时禁止确认。
支持跨器件选择，但每个 case 的器件元数据必须来自目录目录清单/明确映射；不得给
整个批次随意套一个器件名。如果现阶段不能可靠映射，限制单器件并解释原因。

确认提交生成 batch_id 和稳定的逐 case submission_key，防止双击或断线重试重复任务。
提交过程展示“已接收 N / 共 M”；部分失败保留已创建任务及失败项，允许重试失败项。
现有逐任务提交不是原子批量提交，界面不能用一个“成功”掩盖部分成功。
计划预览、确认、幂等批量提交接口为新增需求；不能仅在 GUI 做循环并假设全部接收。

## 4. 任务与回归：批次 -> testcase -> 执行记录 -> 日志

默认批次列表，支持切换 testcase 列表。批次列：名称、revision、flow、总 case 数、
排队/运行/完成数量、PASS/FAIL/TIMEOUT/CRASH/ERROR/CANCELLED、创建时间。
点击批次打开 testcase 表：路径、器件、业务结果、调度状态、工作服务器/slot、耗时、
尝试次数、日志状态。搜索 case；按版本、批次、flow、结果和机器过滤。
结果与调度状态分开：任务结束不代表 PASS；尚无结果不显示为成功。

批次详情展示计数和进度，已取消的 case 单独统计。批次“停止后续任务”只取消未派发
任务，ASSIGNED/RUNNING 不受影响；确认框显示预计影响范围和进行中的数量。
动态状态存在竞态，操作响应展示实际取消数量，不能保证预览数量就是最终数量。

执行详情包含任务参数、flow_config 快照、task_id/run_id、worker_id、调度状态、
业务结果/reason、返回码、开始/结束时间。重试以 run_id 分隔，提供执行尝试切换，
不能用最新结果覆盖掉历史日志。跨主机时钟不同，耗时使用执行机报告的 duration；
缺少可信耗时就显示“未提供”，不跨机器相减。

日志区域提供文件列表与预览。必须覆盖成功、失败、超时、异常的全部执行日志：
stdout.log、stderr.log、run.log（实际生成时）、各阶段工具日志和比较日志，以及
result.env、result.json、实际 flow_config 等执行证据。没有生成的文件明确显示缺失原因。
大体积二进制、checkpoint/bitstream 不作为“日志”默认上传，可作为未来产物功能。
全量日志是本次 run_id 的完整日志文件，不是截断后的末尾几百行。

日志查看支持文本搜索、文件切换、分段加载、跳至末尾、原始文件下载和本次日志包下载。
保留原始字节，遇到非 UTF-8 预览可替换无法解码字符并提示，下载不改变原文件。
ANSI/控制字符安全展示。已归档完整文件提供全文件搜索；只在当前片段搜索时明确标注。

任务完成状态和日志状态独立：未开始、采集中、上传中、已完整归档、部分缺失、上传失败、
已过期。业务已 PASS 但日志上传失败时显示“PASS / 日志待补传”，不能假装日志齐全。
Worker 离线后仍能读 Server 已归档日志。日志失败不改变已有业务判定，单独告警并补传。
首版保证结束后的完整上传和查看；运行中日志的增量查看作为下一步，Figma 可画稿但
必须标“后续能力”，不能承诺现有实时日志。

## 5. 日志落地约束（交给后端实现）

Worker 为每次执行生成文件清单（相对路径、大小、摘要、类型），按 task_id + run_id
向 Server 上传。日志传输按偏移分块、确认、重试、断点续传；重复块必须幂等，结束时
校验长度和摘要。避免把整份日志塞入 task_result 或一个 1 MiB JSON 帧。
新日志传输协议仍可用 TCP+JSON；如二进制使用 base64，块大小需计入编码后的帧大小。
任务结果 ACK、日志上传 ACK、本地日志删除是独立步骤；归档未确认不能删本地副本。
上传队列需要持久化，Worker/Server 重启后能够补传；任务已结束也允许所属历史 run
补日志。超时、Worker 崩溃、清理失败的执行应尽量归档现有日志并标记不完整原因。

服务端保存日志文件和 SQLite 索引，不把大型日志写入任务元数据或热路径缓存。
按相对清单验证文件，防止读取/上传其他任务文件；校验 worker 与 run 的所属关系。
归档路径、单文件/单次执行上限、磁盘预算、保留策略都集中配置。超限/磁盘满必须
报告不完整状态，不能静默截断后声称全量。保留策略尚需部署时明确，画稿不写死天数。

当前 Worker 已保存 stdout/stderr/result.env/flow_config 等局部证据，但没有完整上传
接口，当前 Server 主要保存 execution 摘要。具体 runner 日志需逐一确认产出目录，
以本次 namespace/run_id 收集，不能递归上传整个 SVN 副本或旧 case 的历史日志。

## 6. 补充需求与“增删改查”的业务规则

- 定时计划页面：显示模板、选例范围、版本选择规则、计划启停、下次执行；复用现有
  Templates/Tasks.yaml/clock 概念。CRUD API 需要补齐，首版可以先展示配置。
- 任务列表可重新提交/复制参数，创建新任务。运行中任务、已执行结果不能原地修改。
  模板和计划可编辑；更改只作用于未来提交，历史 flow_config 保持原快照。
- 历史任务提供筛选、导出和归档；物理删除任务、日志和 DB 记录需另定保留规则。
  首版把“删除任务”解释为取消尚未执行任务；历史记录不设计一键永久删除。
- 回退比较：选择同一业务范围、flow 的两个 revision，显示确认的 PASS -> FAIL 和
  FAIL -> PASS，另外列出缺失/new case、TIMEOUT/CRASH，不能把它们等同于回退。
- 连接断开、请求失败、提交重复、查询数据过期、日志未上传、日志过期均需有独立状态。
  操作进度就地反馈，反馈包含实际结果；后端未支持的操作由能力接口隐藏或禁用。

## 7. 现有能力与新增接口

| 页面需求 | 当前可复用 | 待补能力 |
|---|---|---|
| 工作服务器分组/slot 状态 | query_workers/query_status | 机器聚合和 slot 当前任务详情、远程排空控制 |
| 目录树勾选 | clock 的目录扫描逻辑可借鉴 | testcase 目录清单、计数、搜索、目录版本/选择展开 |
| 选择版本与 flow | Server 配置、模板和 ZIP 约定 | 可用版本/模板列表、预览与校验 |
| 批量提交 | submit_task/submission_key/batch_id | 提交计划、逐项确认/幂等重试/部分成功汇报 |
| 批次与 case 查询 | query_batch/query_tasks/query_regression | 批次列表、组合业务筛选、分页聚合 |
| 全部执行尝试 | run_id/retry_count/持久化基础 | 尝试列表与历史证据读取契约 |
| 完整日志 | Worker 本地证据 | 采集清单、上传/补传、索引、读取/搜索/下载 |
| 定时计划管理 | Templates/Tasks.yaml/clock | 安全的查询/修改/启停接口 |

网页不能直接使用现有原生 TCP Socket。Figma 先画与技术栈无关的桌面式界面；后续
若选 Web，需要 HTTP/WebSocket 网关；若选桌面客户端，可直接适配 TCP+JSON。
两者都只能经 Server API 操作，不直接读取 Worker 路径或 SQLite。

## 8. 给 Figma 的画稿任务（可直接粘贴）

请为 ForgeSched 内网 FPGA 回归调度平台设计中文桌面管理界面，以 1440×900 为主。
采用紧凑、清晰、适合大量表格和路径的工程工具风格；浅色优先，深色可作为扩展。
页面包括：工作机分组总览、机器详情/slot 列表、添加任务（test2 目录树三态勾选 +
版本/flow/优先级/超时）、提交预览、部分提交失败、批次列表、批次 case 详情、执行
详情（尝试切换 + 文件日志阅读器）、回退比较、定时计划。

工作服务器名 novarch3/novarch4 为可点击分组栏；每台下面是 slot1/slot2/slot3。
目录树示例使用 kintexuplus/xcku3p-ffvd900-1-i/convergentRoundingEven/run.tcl。
版本示例 18954。工作机、task、case、run_id、batch_id 体现明确父子关系。
日志成功/失败都可查看，日志归档状态与业务结果独立。取消批次仅停止未执行 case。

请提供可编辑组件、Auto Layout、颜色/字体/间距 tokens，以及可点击原型链路：
工作机 -> slot -> 任务日志；添加任务 -> 目录勾选 -> 预览 -> 提交 -> 批次；批次 ->
case -> 历史尝试 -> 日志；选择两版本 -> 回退比较。
所有关键页面补加载、空列表、筛选无结果、连接断开、部分离线、日志上传失败/过期。
大量树节点和表格采用分页/懒加载布局。扩展的机器排空/实时日志操作要明显标为待支持。
用户确认产品交互后再做高保真稿；原型使用明确的示例数据，不冒充真实运行信息。

## 9. 交互验收

1. 看 novarch4 分组能知道在线/忙碌 slot 数，点 slot 能定位对应执行。
2. 父目录勾选全部 case，取消一个子节点后父节点半选；搜索/展开不丢选择。
3. 提交预览精确给出 case 清单、版本、实际 flow_config，重复确认不会重复创建。
4. 停止批次后排队 case 取消，已运行 case 正常结束，操作后数量明确。
5. PASS 和 FAIL 的每次尝试都可查看 Server 归档日志；Worker 下线后仍能访问。
6. 日志未上传/部分缺失/过期与任务结果分别可辨，不能把缺失日志伪装成空日志。
7. 服务断开保留旧数据并标记过期；不会把暂时不可查询显示为所有工作机消失。
